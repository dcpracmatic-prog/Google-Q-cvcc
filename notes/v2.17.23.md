# v2.17.23 — batch_size del verificador invsqrt (dominio completo)

## El bug (medido en Kaggle, kernel 146312858 v6, 2026-11-21)

La demo 2 del notebook de la Skill/Tool llegó hasta el dominio completo
y vetó:

```
dominio completo: veredicto=VETO promoted=0 official=True
verified_by=official S=inf, shots verificados: None
```

La pantalla oficial sí pasó (PASS_PARCIAL, S=74,413.16). El error exacto,
reproducido en sandbox en segundos:

```
verificador oficial FAIL: num_shots must be a multiple of
batch_size=256, got 25067616.
```

El verificador oficial de invsqrt exige `num_shots % batch_size == 0`
con batch por defecto 256. El dominio completo a 8 shots/x son
25,067,616 shots y 25,067,616 % 256 = 96. La pantalla (4,096 shots)
pasaba porque 4,096 % 256 == 0. Por eso el fallo era rápido (~2 min)
y no un problema de memoria ni de tiempo.

El kernel v6 de H1 sí completó el dominio completo (25,067,616 shots)
porque llamaba a la API Python con `batch_size=224` (224 divide a
25,067,616). El CLI acepta `--batch-size` igual.

## El arreglo

- `auto_mvp/vqcc/verify.py` (`verify_circuit_file`): se pasa
  `--batch-size = gcd(num_shots, 256)` al verificador (invsqrt y DQI).
  Es el mayor divisor de num_shots que sea <= 256: 256 en pantalla y
  en el default de 64 shots/x, 32 en el dominio completo a 8 shots/x.
  No cambia qué shots se corren, solo el tamaño del lote.
- `tests/test_skill_chain.py`: nuevo test
  `test_verify_batch_size_divide_num_shots` (8 tests en el archivo):
  max_x=100, 8 shots/x (800 shots; 800 % 256 = 32, fallaba antes;
  gcd(800, 256) = 32, 800 % 32 == 0). Mide ok=True,
  verified_by=official-partial, verified_shots=800, S=72,330.16
  (el S depende del rango de x; a max_x=100 no es el S del dominio
  completo, 74,400).
- Versión 2.17.23 (`auto_mvp/__init__.py`, `pyproject.toml`).

## Medición
