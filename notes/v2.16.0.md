# v2.16.0 — El LLM ya optimiza el DQI durante la ejecución (2026-11-14)

Pedido de Arturo (2026-11-14): el LLM se metió para que optimice
durante la ejecución. En v2.15 el generador híbrido existía pero el
LLM no lo tocaba. Ahora sí: el estratega mueve los knobs del
generador y solo sobrevive el menor S.

## Qué se añadió

- **`auto_mvp/llm_auto_dqi.py`** — corredor LLM para DQI. El modelo
  (estratega, nunca constructor) lee los mejores knobs medidos
  (batch, nslot, toom3) con su Q/T/S y el historial, y propone un
  lote de deltas como JSON: `{"deltas": [{"batch": 17, "nslot": 36,
  "toom3": true, "seed": 1, "reason": "..."}, ...]}`. Cada delta se
  materializa con `build_hybrid_bm_circuit` y se mide Q/T/S
  (S = R * Q^2 * T, R=1.1912605); solo el menor S sobrevive. La
  validez la impone `verify_small` (sigma correcto y scan limpio).
  Sin llave, sin red o con JSON malo, el corredor sigue con los
  knobs por defecto (batch/nslot rotando, toom3 alternando): la
  corrida nunca depende del modelo. La llave va en el entorno
  (`GEMINI_API_KEY` / `GROQ_API_KEY`; en Kaggle, como secreto).
- **Toom-3 vendoreado en el repo** (`auto_mvp/circuits/generators/`):
  `toom3.py` + `mult51.py` (el emisor verificado del sandbox,
  500/500 + bordes) + `poly_mul_2.txt` + `poly_mul_6.txt`.
  `CIRC_DIR` ahora es el directorio del módulo en el repo (antes
  era la ruta del sandbox). `emit_ixor_toom3` verificado 4/4 en el
  repo incl. target no cero (acumula: target ^= f*g).
- **`build_hybrid_bm.py`: knob `toom3`** — `build_hybrid_bm_circuit
  (..., toom3=True)` usa Toom-3 (45 T/mult) en vez del nativo
  (63 T/mult); `verify_small(..., toom3=True)` lo verifica; CLI
  `--toom3`. El flag es de módulo (`set_toom3`) porque
  `ixor_gf2_mul` se llama directo en bm_forward, compute_omega,
  montgomery_batch, hybrid_scan y bm_backward.
- **`tests/test_llm_dqi.py`** — 4 tests (S proyectado, parse de
  deltas, mejora con toom3, sin llave sigue con defecto).
- **`tests/test_hybrid_bm.py`** — +2 tests (toom3 baja T sin subir
  Q; verify_small con toom3 PASS).
- `auto_mvp/llm_auto.py`: el docstring ya no dice que el
  materializador DQI está pendiente (ahora existe y tiene corredor).

## Medido (verificado, sandbox)

- Nativo `ixor_gf2_mul`: 63 T/mult. Toom-3: 45 T/mult (-18 T/mult).
- Escala chica (n=10, m=15, batch=4, nslot=6): nativo T=27,264,
  Toom-3 T=22,152 (-5,112, -18.8%), Q igual (1,139).
- Escala completa (n=70, m=4095, batch=17): nativo Q=6,791
  T=1,900,947 S=1.04e14; Toom-3 Q=6,791 T=1,519,563 (-20.1%)
  S=8.35e13. Q no sube (las ancillas Toom-3 se reutilizan).
- `verify_small` con toom3=True: PASS (sigma 24/24, scan 12/12).
- Corredor LLM-DQI a escala chica (cliente falso): 1 llamada LLM,
  0 fallbacks, 3 propuestas, 0 inválidas; el mejor es
  batch=4, nslot=6, toom3=True, Q=1,139, T=22,152, S=3.42e10
  (la base nativa era S=4.21e10: el LLM propuso toom3 y el
  corredor lo guardó). Sin llave: 0 llamadas, 1 fallback, la
  corrida sigue con los knobs por defecto.
- Tests: 17/17 (test_llm_dqi 4 + test_hybrid_bm 5 + test_llm_v220 8).

## Alcance honesto

- El LLM ya optimiza el DQI durante la ejecución, pero solo mueve
  los knobs que existen (batch, nslot, toom3). El S con Toom-3
  (8.35e13) sigue siendo 3.4x peor que el baseline (2.44e13).
  La reducción de Q hacia ~1,414 (reutilización de slots S +
  reconstrucción de B, `PLAN_SLOT_REUSE.md`) sigue siendo el
  siguiente paso arquitectónico; el LLM no puede proponer un knob
  que no está implementado.
- El LLM real no se probó en este entorno (no hay llave
  `GEMINI_API_KEY`/`GROQ_API_KEY` aquí); el corredor se probó con
  cliente falso y con el fallo sin llave (que cae al defecto).
  Con llave en Kaggle, el cliente real (`complete_json`) es el
  mismo que usa el corredor invsqrt.
- La suite completa no se re-corrió entera en este cambio (solo
  los 17 tests de los módulos tocados); el cambio añade archivos
  nuevos y un knob, y no modifica el operador invsqrt.
