# v2.17.24 — Arreglo del bug sys.modules/dataclasses al cargar verificadores

El bug bloqueó dos kernels (R14 DQI y F3 I1) con cero medido:
cargar `verify_submission_invsqrt.py` con `spec_from_file_location` +
`module_from_spec` + `exec_module` sin registrar el módulo en
`sys.modules` falla con `AttributeError: 'NoneType' object has no
attribute '__dict__'`.

## Causa raíz (medida)

El verificador usa `from __future__ import annotations` +
`@dataclasses.dataclass(frozen=True)` en `ProblemSpecInvSqrt`.
Al decorar la clase, `dataclasses._is_type` (CPython 3.12) hace
`sys.modules.get(cls.__module__).__dict__`; la clase tiene
`__module__` igual al nombre del spec, pero el patrón del notebook
nunca lo registra, así que `.get()` devuelve `None`. Como CLI
(`__main__`) no falla porque `sys.modules["__main__"]` sí existe.
Reproducido en sandbox (venv Python 3.12.3) con el traceback
idéntico al de los kernels.

## Lo que quedó

- **Helper canónico `auto_mvp/module_loading.py::load_module_from_path`**
  (una línea es el arreglo: `sys.modules[name] = mod` antes de
  `exec_module`). Toda carga dinámica por ruta en el repo pasa por él.
- **5 sitios buggy unificados al helper:** `auto_mvp/autonomous.py`
  (3 cargas de código LLM `novel_nslot`/`novel_seed`),
  `auto_mvp/notebook.py` (plantilla `_MODULE_CELL` — los notebooks
  generados heredaban el bug), `tests/test_skill_chain.py`
  (`_load_module`). `auto_mvp/circuit.py` (2 cargas de
  verificadores) y `tests/test_auto_mvp_v091.py` ya tenían el
  registro inline y ahora usan el helper.
- **Regresión `tests/test_sysmodules_dataclass.py` (3 tests):** el
  patrón viejo falla con el AttributeError exacto (subproceso),
  el helper carga el verificador vendado (`for_n_p(10, 1)` →
  max_x 3,133,452), y la plantilla registra antes de `exec_module`.
- `tests/test_skill_chain.py`: el assert de versión sube a 2.17.24
  (`run_vqcc_chain` devuelve `__version__` del paquete).
- Versión 2.17.23 -> 2.17.24 (`auto_mvp/__init__.py`,
  `pyproject.toml`).
