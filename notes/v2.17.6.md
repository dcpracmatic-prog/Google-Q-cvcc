# v2.17.6 — Auditoría: el optimizador no podía mejorar porque el batch estaba restringido (2026-11-14)

## El problema (pedido de Arturo: "audita por qué pasa y corrigelo")

La corrida v2.17.4 en Kaggle (kernel 145059966) verificó que la
corrección de ancilla funciona (ancilla 0, S restaurado, T
dinámico = estático), pero el optimizador NO mejoró: la mejor
semilla fue la base misma (batch=4, nslot=6, S=4.418e10). El LLM
no encontró nada mejor.

## La auditoría (medido, no supuesto)

**1. El mapa de S a n=10, m=15 (nslot=6) muestra que SÍ había mejora:**

| batch | Q | T | S |
|---|---|---|---|
| 1 | 1067 | 29481 | **3.9983e10** (9.5% mejor) |
| 2 | 1091 | 29019 | 4.1147e10 (6.9% mejor) |
| 3 | 1115 | 28701 | 4.2506e10 (3.8% mejor) |
| 4 (base) | 1139 | 28587 | 4.4180e10 |
| 5 | 1163 | 28473 | 4.5877e10 (peor) |
| 8 | 1235 | 28359 | 5.1527e10 (peor) |

Más nslot también es peor (nslot=8: 6.09e10; nslot=12: 1.03e11).
batch=1, nslot=6 es VÁLIDO (verificado de punta a punta: ancilla
0, S restaurado, errores de valor 0, T dinámico = estático).

**2. La causa: el batch estaba restringido a {4, 8, 17, 36}.**

- `llm_auto_dqi.py` línea 82: `_DEFAULT_BATCH = (4, 8, 17, 36)`.
- El prompt del LLM decía `"batch": 4|8|17|36` (solo esos 4).
- El fallback rotaba solo esos 4.
- `autonomous.py` tenía la misma restricción (línea 100, prompt
  línea 387) Y además redondeaba cualquier batch al más cercano
  de {4, 8, 17, 36} (línea 979-980).

Dentro de {4, 8, 17, 36}, el mejor batch ES 4 (la base). **No
había mejora posible en ese conjunto.** El LLM nunca podía
proponer batch=1, 2, 3, y el fallback tampoco los probaba.

Por qué batch=1 gana a escala chica: S = R·Q²·T y Q² domina.
batch pequeño = menos qubits (Q baja de 1139 a 1067) aunque T
suba un poco (28587 a 29481). A escala grande el equilibrio
cambia (por eso 17 era el batch de v2.15), pero a escala chica
el batch pequeño gana.

**3. Segunda capa: el LLM sube nslot cuando varía batch.**

Con el batch ya ampliado, el LLM real (Qwen 1.5B) propuso
batch=1 y batch=2, PERO con nslot=7, 9, 10, 13 (en vez de 6).
Subir nslot añade qubits y S sube (batch=1, nslot=7:
S=4.726e10, peor que la base). El modelo no sigue la pista de
"nslot mínimo es mejor" y varía todo a la vez. La combinación
ganadora (batch=1, nslot=6) nunca la propuso el LLM.

## La corrección

- **`llm_auto_dqi.py`:**
  - `_DEFAULT_BATCH = (1, 2, 3, 4, 8, 17, 36)`.
  - Prompt: `"batch": 1..64` + pista medida (batch pequeño baja
    Q y S a escala chica; nslot mínimo suele ser lo mejor).
  - **Barrido sistemático** antes del bucle LLM: mide batch=1, 2,
    3 con nslot mínimo (fuerza bruta sobre circuitos: se mide el
    circuito real). Respeta max_proposals y el presupuesto de
    tiempo. Así el corredor GARANTIZA encontrar la mejora aunque
    el LLM no la proponga.
- **`autonomous.py`:**
  - `_DEFAULT_BATCH = (1, 2, 3, 4, 8, 17, 36)`.
  - Prompt y regla de código-repo: `"batch": 1..64`.
  - El redondeo de novel_seed ya no fuerza un valor discreto:
    solo limita a 1..64.

## Medido (verificado, sandbox, LLM real Qwen2.5-Coder)

- `run_llm_auto_dqi` (n=10, m=15, max_proposals=6, batch_size=2):
  **best_S = 3.9983e10, mejora 1.105x vs la base 4.418e10**,
  best_knobs batch=1, nslot=6, toom3=False, Q=1067, T=29481.
  llm_calls=2, fallbacks=0, proposals=6, valid=7, invalid=0.
  Antes de la corrección: best_S = base (mejora 1.000x).
- Tests: **28/28** (llm_dqi + autonomous + hybrid_bm + llm_v220).
  Se actualizaron los valores esperados (mejor semilla ahora
  batch=1, Q=1067, T=29481, S=3.9983e10).

## Alcance honesto

- La mejora es a escala chica (n=10, m=15). A escala completa
  (n=70, m=4095) el batch óptimo puede ser otro; el barrido
  sistemático también corre ahí (batch 1, 2, 3 con nslot mínimo)
  y el LLM explora desde el mejor.
- La fase del scan sigue con errores (3-4/8, varía con la
  semilla del simulador; apunta al HMR). Es un problema aparte,
  no lo toca esta versión.
